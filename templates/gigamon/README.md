# Gigamon templates for Zabbix 7.0 (SNMP, built from the vendor MIBs)

**Status: offline-validated only. Not imported into a Zabbix server, not run against a Gigamon device.** Do not alert on it in production before the lab checks at the bottom.

File: `zbx_templates_gigamon_snmp.yaml` — one import, four independent templates (Data collection → Templates → Import):

| Template | Link to | Source MIB | Covers |
|---|---|---|---|
| Gigamon GigaVUE by SNMP | every GigaVUE node | MIB-II / IF-MIB | ICMP + SNMP availability, sysDescr/Name/ObjectID/uptime, interface discovery (oper/admin status, speed, 64-bit bps in/out, errors, discards), link-down and error triggers |
| Gigamon GigaVUE Inline Bypass by SNMP | nodes with inline bypass only | GIGAMONINLINEBYPASS (…26866.4) | per inline **tool**: aggregate status, heartbeat, negative heartbeat, port A/B; per inline **network**: forward state (10 states), port A/B |
| Gigamon GigaVUE GigaSMART by SNMP | nodes with GigaSMART only | GIGAMONGIGASMART (…26866.5) | eport heartbeat + Tx/Rx rate, eport interface admin/link/speed, tunnel gateway/destination status, GSOP NetFlow resource failures, eport count |
| Gigamon GigaVUE-FM by SNMP traps | the GigaVUE-FM appliance/VM | GIGAMON-FM-SNMP (…26866.6) | the 41 FM notifications as SNMP traps (catch-all log item + 10 grouped problem triggers) |

Why four: discovery rules on a feature the node lacks go *Not supported*, and FM has no pollable objects at all. Link only what exists.

## What is NOT covered (read this)

1. **No chassis hardware health** (fans, PSUs, temperature, CPU/memory, ports, maps, cluster). That is `GIGAMON-SNMP-MIB`, which was not among the three files. Send it and I will add it; until then hardware faults on the node are invisible to this template set.
2. **GIGAMON-COMMON-SMI was not supplied**, and it defines `TUNGWSTATUS` and `TUNDESTSTATUS`. The tunnel gateway/destination statuses are collected as raw integers and their triggers are **disabled** (`{$GIGAMON.GS.TUNNEL.GW.OK}` / `{$GIGAMON.GS.TUNNEL.DEST.OK}` = 0). Set them to the integer that means "healthy" after reading the enum from the full MIB or a live `snmpget`.
3. `tunnelGwStatus` is declared **MAX-ACCESS accessible-for-notify**: per SMI it is not readable by GET/WALK. The device may allow it anyway; if the item goes Not supported, that is why.
4. `txUtil`/`rxUtil` (GigaSMART eport interface) are OCTET STRINGs with no documented format and are not collected. `ePortTxCount/RxCount` are Counter64 of unspecified unit (stored as a rate).
5. FM notification payload (severity/description) is only in the trap text; triggers are by notification identity, not severity.

## MIB findings that affect correctness

- All Gigamon OIDs and all value-map entries in the YAML are **generated by parsing your MIBs** (`tools/gen_gigamon.py` + `tools/mibtree.py`), not typed by hand.
- `gsopStatsTable` carries the comment `1.3.6.1.4.1.26866.5.7`, but it is defined as `{ gigaSmartStatus 7 }` and `gigaSmartStatus` is `…26866.5.1`, so the real OID is **`…26866.5.1.7`**. The template uses the computed one. If a live walk shows data at `…5.7`, the vendor comment was right and the MIB is wrong; tell me.
- `numberofeports` is a scalar: the instance `.0` is appended.
- The Inline and GigaSMART MIBs import `gigamonSnmp` from GIGAMON-COMMON-SMI while GIGAMON-FM-SNMP defines it itself; harmless for Zabbix (numeric OIDs), relevant only if you load MIBs into snmptrapd.
- Inline `intPortAStatus`/`inlNetworkPortAStatus` etc. use value 0 for **Disabled**; disabled is never alarmed.

## Setup

1. Host with an **SNMP interface** (SNMPv2c or v3 — Counter64 and ifHC* need it; v1 will not work). Allow the Zabbix server/proxy in the node's SNMP ACL. Link *Gigamon GigaVUE by SNMP* plus the feature templates.
2. Review macros; most important ones:
   - `{$GIGAMON.INLINE.NET.CONTROL:"<network alias>"}=0` silences a network during maintenance (bypass triggers are expected then); same for `{$GIGAMON.INLINE.TOOL.CONTROL:"<tool alias>"}`, `{$GIGAMON.GS.EPORT.CONTROL:"<id>"}`, `{$GIGAMON.GS.IF.CONTROL:"<ifName>"}`, `{$GIGAMON.IFCONTROL:"<ifName>"}`.
   - `{$GIGAMON.IF.NAME.NOT_MATCHES}` to exclude interfaces from discovery.
3. **FM traps**: host = the FM address (the trap source IP must equal the host's SNMP interface IP). On the Zabbix server: `snmptrapd` + `zabbix_trap_receiver.pl` (`traphandle default /usr/bin/zabbix_trap_receiver.pl`, authCommunity/user matching FM's trap config), `StartSNMPTrapper=1`, `SNMPTrapperFile=…`. The template matches both the numeric OID (`26866.6.1.N`) and the MIB name, so it works with or without the MIB loaded in snmptrapd. Traps that match nothing land in `snmptrap.fallback`. FM trap problems have **no automatic recovery** (healthy-state traps exist but a trap pair cannot be correlated safely): close them manually.

## Triggers (defaults)

Inline network forward state: `failure-introduced-drop` DISASTER; failure-introduced-bypass / network-ports-forced-down / abnormal-forwarding HIGH; network-disconnected AVERAGE; physical-bypass / forced-bypass / forced-bypass-monitoring WARNING (tools not inspecting). Inline tool: aggregate down HIGH, heartbeat down (only when aggregate not already down) HIGH, negative heartbeat WARNING, port A/B down AVERAGE. Eport heartbeat down HIGH; eport interface link not up while admin up AVERAGE; NetFlow resource failures increasing 15 min WARNING. Node: ICMP down HIGH, no SNMP AVERAGE, restart INFO, interface up→down AVERAGE (only on transitions: tap ports without link are normal), interface errors WARNING. FM: fabric-node failure / V Series unhealthy HIGH; session unhealthy, traffic-drop, licence expired, disk, cluster/HA, upgrade failed AVERAGE; licence expiring, flow events WARNING.

## Validation performed (offline)

`python3 tools/validate_gigamon.py` (needs the vendor MIB files; edit the paths at the top of the script) (reads the YAML back, independent of the generator): UUIDs unique and v4-shaped; every Gigamon OID exists in the supplied MIBs and is a readable column (flags accessible-for-notify); standard OIDs checked against an independent list; every value map equals the MIB enumeration; every enum comparison in a trigger uses a value that exists in that enum; Counter64 items have change-per-second; trigger/recovery expressions reference existing keys, balanced, only known functions; prototype names carry LLD macros; macros used = macros defined; trap regexes tested against numeric and named trap text for all 41 notifications (no over-match, no payload-OID false match). Mutation tests: 7 deliberate breaks (wrong column, the commented gsop OID, out-of-range enum, altered map entry, bad key, lost Counter64 rate, trap trigger without manual close) were each caught.

**Not tested:** Zabbix import, real SNMP responses, trap receipt, the unverified points listed above.

`python3 tools/check_limits.py` (no MIBs needed): every trigger-function and preprocessing parameter <= 255 chars (limit confirmed by the Zabbix 7.0.30 importer) plus recalled schema limits for names, keys, OIDs, expressions, macros, tags, value maps. Longest parameter now 208 chars.
