## 2. Live order (smallest blast radius first)

1. **LAB setup**: create a LAB API token for the SLA platform; `cp config/.env.example .env`; set `ZABBIX_SLA_URL_LAB` / `ZABBIX_SLA_TOKEN_LAB`. Confirm `{$NETOPS.ENVIRONMENT}` = `lab` (alerting `--init-identity` if absent - this project refuses to write without it).
2. **E-01 / A-01** `python3 scripts/accept_tag_semantics.py --env lab --host <monitored host> --item-key <item with data>`. Only `RESULT: AND` lets you continue: then set `tag_semantics: and` in `inventory/lab.yaml`. If it prints OR, stop and report: the per-link design must change to SLA-owned signal triggers (HLD §3).
3. `./sla.sh --env lab check` → `plan` (read-only; nothing on LAB yet) → `apply`. Expect 32 services, 2 SLAs, `readback verification: PASS`.
4. **A-02** `python3 scripts/accept_api_shapes.py --env lab` (needs step 3). Any FAIL = a model assumption was wrong; fix list in section 4.
5. A-06..A-08 (idempotence, drift, ownership), A-19 (rollback incl. partial failure), A-04 (isolation).
6. Failure injection A-09..A-14 in the LAB lab (INT-CORE/STC/MOBILY/SAIX interfaces), recording service status and the actual routing behaviour (answers E-06).
7. A-15 `quality`, A-17 `report` against Zabbix's own SLA report, A-18 planned downtime.
8. Probes (A-16) only after E-04..E-07 are answered; dashboards (A-20) after building the reference dashboard; reporting render (A-21) after the adapter.

Put every transcript and screenshot in `zabbix-sla/evidence/` (Git-ignored by the repository rule - attach it to your hand-back; commit only `docs/ACCEPTANCE-RESULTS.md`) and fill `docs/ACCEPTANCE-RESULTS.md` (template at the end of ACCEPTANCE-MATRIX.md).

## 3. Known limitations (stated, not hidden)

| # | Limitation | Consequence |
|---|---|---|
| L-1 | AND/OR semantics of several service problem tags is unproven (E-01) | `check` fails and nothing is applied while the inventory says `tag_semantics: unknown` (the shipped state); `--assume-tag-semantics and` permits a read-only `plan` only |
| L-2 | Mock enforces documented validation only | Zabbix may reject or reshape something the mock accepts (A-02 exists for this) |
| L-3 | `sla.getsli` parameters (`period_from`, `period_to`, `serviceids`) and the response layout `sli[period][service]` are from the documentation | `report` may need a one-line change after A-02/A-17 |
| L-4 | Probe items: `icmpping` result usable in a calculated sum, `interfaceid` handling for simple checks, `nodata()` on a calculated item | untested live; probes ship `proposed` and are deferred |
| L-5 | Dashboard widget field type ids/names are unverified defaults | `dashboards apply` is refused until `scripts/accept_widget_fields.py` has produced evidence |
| L-6 | Partial signal coverage: SAIX-CORE and PALO-LAB are not monitored | a far-end failure that keeps the monitored end up/up is invisible; reported as a caveat (A-14) |
| L-7 | Inter-site and National fallback via transit are modelled **absent** | `svc.inter-site` has a single modelled path (no redundancy represented, noted at compile time) until a failover test proves otherwise |
| L-8 | Security-edge links to PALO-LAB are components but are in no path | their role is unknown (E-13) |
| L-9 | No device layer, no application services | no application list / addresses were supplied (E-05); no placeholders are applied |
| L-10 | SLOs are placeholders (`approved: false`) | accepted in LAB, refused in Production |
| L-11 | Rollback recreates objects with new ids | saved links/dashboards pointing at ids must be re-resolved (dashboards are regenerated by name) |
| L-12 | First month after creation is partial: Zabbix probably has status history only from service creation (confirm in A-17) | reports say `INSUFFICIENT_DATA` / `partial_period` instead of a figure |
| L-13 | The reporting suite cannot yet render an externally supplied document | one small adapter on its side (INTEGRATION-REPORTING.md); the JSON deliverables exist now |
| L-14 | Service `status` propagation rules, weights and `like` operators are left at defaults / unused | revisit if the GUI shows unexpected severities |

## 4. If a live check fails

Report the failing ID, the request/response (redact tokens) and the Zabbix version. Likely fix locations: field names/enums → `slaas/state.py` + `slaas/apply.py` builders; getsli layout → `slaas/reporting.py::_parse_sli`; widget fields → regenerate evidence; tag semantics → HLD §3 contingency. Update `tests/fake_sla.py` to reproduce the real behaviour **first**, then fix the code.
