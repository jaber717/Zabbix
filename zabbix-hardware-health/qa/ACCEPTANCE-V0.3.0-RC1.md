## Release-blocking security reproductions

All five checks in [`acceptance_v03_security_repro.py`](acceptance_v03_security_repro.py) ran against the **actual template manager** with an offline fake transport and reported CONFIRMED. No live write was made.

1. **Copied marker adopts an operator template.** `tplmgr.plan` treats a same-name foreign template with copied `managed_by`/definition marker as owned, then `tplmgr.apply` calls `configuration.import` on it. There is no independent ownership record or exact ID binding (`hwh/tplmgr.py:22–46,57–75`).
2. **Manual content changes are invisible.** A live template carrying the expected description hash but an operator-added item makes `plan`/`apply` return `noop` without exporting or comparing actual contents (`hwh/tplmgr.py:45–46`). Also disclosed as L17 in `docs/KNOWN-LIMITATIONS.md`.
3. **Rollback can delete a recreated template.** After an owned template was created, replacing it in the fake API with a different ID but the same name/marker made `rollback` call `template.delete` for the new ID (`hwh/tplmgr.py:86–100`). Backup has no created template ID or nonce.
4. **Linked template update proceeds.** A linked, marker-bearing template was reported as linked but still passed to `configuration.import` (`hwh/tplmgr.py:47,57–75`). The impact of updating linked hosts has not been safely bounded.
5. **Unrelated children are deletion candidates.** Import rules enable `deleteMissing=True` for discovery rules, items and triggers (`hwh/template.py:212–214`). This is directly destructive on update when the current template contains children not in the generated source. Official Zabbix 7.0 `configuration.importcompare` documents that `deleteMissing` deletes objects absent from the import: https://www.zabbix.com/documentation/7.0/en/manual/api/reference/configuration/importcompare . The offline reproduction confirms the exact flags; no live deletion was attempted.

The fixed, name-derived backup path is overwritten on a later update, so a prior pre-change export can also be lost. The installer preserves config/state directories across release switches, but that does **not** establish Zabbix template ownership or make object rollback safe.

**Minimum correction before import approval:** bind ownership and rollback to a persisted exact template ID plus independent nonce/UUID; re-read and export live content immediately before any write and fail closed on drift; prohibit or require explicit review of linked-template updates; use non-destructive import rules or prove ownership of each deletable child; keep immutable per-operation backups; verify IDs again immediately before delete/restore. Repeat these independent sequences and a read-only importcompare before a separately approved LAB import.

No real device was polled in this acceptance.
- Nexus `entSensorStatus` is sensor operability, not over-temperature. The candidate labels its discovered status as temperature sensor health but filters merely for a present value; non-temperature sensor types may enter until device evidence establishes a class filter (documented L10). FortiGate generic alarms do not prove a particular fan/PSU/temp exists. Huawei temperature is informational without threshold; PAN-OS thermal path is PA-440-specific. ASR8500/FortiProxy unsupported. `config/device-evidence.yaml` has no REAL DEVICE VERIFIED entries. No unsupported vendor capability was promoted to real verification.
- PAN-OS `configuration.importcompare` success does not validate real XML API authentication, privileges, response shape on the target model or secret-macro provisioning. Physical-device coverage, live import, host linking, trigger behavior and notification delivery remain unverified.

**Conclusion:** Read-only/offline compatibility is promising, but the template write path is unsafe. This candidate is **NO-GO for separately approving a live LAB template import** until the five reproduced issues are fixed and retested. Production readiness is not claimed.
